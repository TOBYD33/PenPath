## Task

Add a **Client Link Generation** feature to PenPath. This lets Admin, Super Admin, and any user
explicitly granted the `GENERATE_CLIENT_LINK` permission create a trackable, single-use,
expirable application link and send it to a client, so the client can fill their intake form
remotely instead of coming into the office.

This feature must integrate with the **existing** Case Assignment flow — a case created from a
link goes into the same unassigned queue as a scanned physical-form case. Do not create a
separate assignment path.

## 1. Database Changes

Add to the existing Prisma schema (extend, do not restructure existing models):

```prisma
model UserPermission {
  id          String     @id @default(cuid())
  userId      String
  user        User       @relation(fields: [userId], references: [id])
  permission  Permission
  grantedById String
  grantedAt   DateTime   @default(now())

  @@unique([userId, permission])
}

enum Permission {
  GENERATE_CLIENT_LINK
  ASSIGN_CASE
}

model ClientLink {
  id            String     @id @default(cuid())
  token         String     @unique
  generatedById String
  generatedBy   User       @relation("LinkGeneratedBy", fields: [generatedById], references: [id])
  clientName    String?
  clientPhone   String?
  clientEmail   String?
  status        LinkStatus @default(UNUSED)
  expiresAt     DateTime
  usedAt        DateTime?
  caseId        String?    @unique
  case          Case?      @relation(fields: [caseId], references: [id])
  createdAt     DateTime   @default(now())
}

enum LinkStatus {
  UNUSED
  USED
  EXPIRED
  REVOKED
}
```

Update `User` model to add:
```prisma
permissions    UserPermission[]
linksGenerated ClientLink[] @relation("LinkGeneratedBy")
```

Update `Case` model to add:
```prisma
clientLink   ClientLink?
assignedById String?   // who assigned this case: Admin, Super Admin, or Supervisor
```

Run the migration after confirming the schema diff looks correct against the existing DB.

## 2. Backend — API Endpoints

Build these under RBAC middleware (reject with 403 if the caller lacks the right role/permission):

| Endpoint | Method | Who can call | Behavior |
|---|---|---|---|
| `/api/links` | `POST` | Admin, Super Admin, or user with `GENERATE_CLIENT_LINK` | Creates a `ClientLink`: generates a cryptographically random `token`, sets `expiresAt` (default now + 7 days, override via request body), stores optional `clientName/Phone/Email`. Returns the full shareable URL. |
| `/api/links` | `GET` | Admin, Super Admin, or user with `GENERATE_CLIENT_LINK` | Lists links generated by the caller (or all links, if Admin/Super Admin), with status, expiry, and linked case if used. |
| `/api/links/:id/revoke` | `POST` | Admin, Super Admin, or the original generator | Sets `status = REVOKED`. Reject if already `USED`. |
| `/api/apply/:token` | `GET` | Public (no auth — this is the client-facing entry point) | Validates the token: exists, `status = UNUSED`, not past `expiresAt` (auto-flip to `EXPIRED` and reject if so). Returns the dynamic form schema (PFA/PMB selection + bio-data fields) plus any pre-filled `clientName/Phone/Email`. |
| `/api/apply/:token` | `POST` | Public | Validates token again (same checks). On success: creates the `Case` (via the **same case-creation service function** used by the physical-scan intake path — do not duplicate logic), sets `intakeSource = DIGITAL_LINK`, links `ClientLink.caseId`, sets `ClientLink.status = USED` and `usedAt = now()`. Case enters status `NEW_APPLICATION` and appears in the Case Assignment queue. |
| `/api/users/:id/permissions` | `POST` / `DELETE` | Admin, Super Admin | Grants/revokes `GENERATE_CLIENT_LINK` or `ASSIGN_CASE` for a given user. Every change writes an `AuditLog` entry (old value → new value, who made the change). |

**Reuse existing logic:** if there is already a `createCaseFromSubmission()` (or similarly
named) service function used by the physical-scan intake flow, call that same function from
the link-submission endpoint. Do not fork case-creation logic between the two intake paths —
this is a hard requirement, not a suggestion.

## 3. Frontend — New Screens

1. **"Generate Application Link" screen** (Admin, Super Admin, and any user with
   `GENERATE_CLIENT_LINK`, accessible from their dashboard nav):
   - Optional fields: client name, phone, email
   - Optional expiry override (default 7 days)
   - On submit: shows the generated link with copy-to-clipboard, plus quick-send buttons
     (email/SMS/WhatsApp share, if those integrations exist — otherwise copy-only is fine for
     v1)
   - Below the form: a table of links this user has generated, showing status
     (Unused/Used/Expired/Revoked), client name if provided, generated date, expiry, and a
     "Revoke" action for unused links

2. **Public client application page** at `/apply/:token`:
   - No login required
   - On load, validates the token via `GET /api/apply/:token`; show a clear "This link has
     expired or already been used" state if invalid — do not expose why (used vs. expired vs.
     revoked) beyond that generic message, to avoid leaking internal state to an unauthenticated
     visitor
   - If valid: renders the same dynamic PFA/PMB selection + bio-data form used elsewhere in the
     app (reuse the existing form-rendering component — do not build a second form renderer)
   - Pre-fills name/phone/email if the link included them, but keeps fields editable
   - On submit: `POST /api/apply/:token`, then show a clear confirmation screen ("Your
     application has been received — our team will be in touch")

3. **Permission management UI** (Admin, Super Admin — likely inside the existing user
   management screen from Phase 1):
   - Add a toggle or checkbox per user for `GENERATE_CLIENT_LINK` and `ASSIGN_CASE`
   - Reflect current grant state; changing it calls the permission endpoint immediately

4. **Case Assignment queue update:**
   - Add an "Intake Source" column/badge (`Digital Link` / `Physical Scan`) purely for visibility
   - For link-originated cases, show who generated the link and (if provided) the pre-filled
     contact info, so the Supervisor/Admin/Super Admin has context when assigning
   - Assignment action itself should now also be available to Admin and Super Admin, not just
     Operation Supervisor — reuse the existing assignment component/logic if it already exists,
     just widen the RBAC check

## 4. Business Rules to Enforce (write tests for each)

1. A link can only be generated by Admin, Super Admin, or a user holding `GENERATE_CLIENT_LINK`
   — enforced server-side, not just hidden in the UI.
2. A link is single-use: once `USED`, resubmission via the same token must be rejected.
3. A link past `expiresAt` must be rejected on both `GET` and `POST` to `/api/apply/:token`,
   and its status should be lazily flipped to `EXPIRED` on that failed access (or via a
   scheduled job — either is acceptable, document which one you chose).
4. `intakeSource` must never change validation, approval, or workflow behavior — the same case
   pipeline runs regardless of how the case was created.
5. Case assignment (from either intake path) can only be performed by Admin, Super Admin, or a
   user holding `ASSIGN_CASE`.
6. Every permission grant/revoke and every case assignment writes an `AuditLog` entry.
